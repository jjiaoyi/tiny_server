# TinyWebServer 第一版说明

## 1. 项目定位

TinyWebServer 是一个使用 C++17 编写的轻量级 Web 服务器项目，主要用于学习 Linux 网络编程、理解 WebServer 基本工作流程。

第一版的目标不是实现工业级 HTTP 服务器，而是把一个 WebServer 的核心链路跑通：

- 能监听端口并接收 TCP 连接。
- 能使用非阻塞 socket 和 epoll 管理多个客户端连接。
- 能通过线程池处理客户端请求。
- 能解析基础 HTTP 请求并返回 HTTP 响应。
- 能访问静态文件并提供一个简单 JSON 接口。
- 能支持 HTTP/1.1 keep-alive 和空闲连接清理。

## 2. 当前架构

第一版采用简化 Reactor 架构：

```text
客户端
  |
  v
listen socket
  |
  v
主线程 epoll_wait
  |
  +-- listen fd 可读：accept 新连接
  |
  +-- client fd 可读：投递任务到线程池
                         |
                         v
                    worker 线程
                         |
                         +-- recv 读取请求
                         +-- HttpParser 解析请求
                         +-- 构造 HttpResponse
                         +-- send 返回响应
                         +-- keep-alive 则重新注册 epoll
```

主线程负责事件监听、连接接收、任务分发和空闲连接清理。worker 线程负责具体的客户端请求处理，包括读取 socket、解析 HTTP、读取静态文件、构造响应和发送响应。

## 3. 模块划分

项目主要分为以下模块：

- `net`：网络核心模块，包含 `TcpServer`、`EpollPoller` 和 socket 工具函数。
- `http`：HTTP 模块，负责请求解析和响应构造。
- `thread`：线程池模块，负责固定数量 worker 线程和任务队列。
- `log`：异步日志模块，前台线程写缓冲，后台线程定时刷盘。
- `util`：工具模块，负责文件读取、路径处理和 MIME 类型判断。

主要目录结构：

```text
include/
  net/
  http/
  thread/
  log/
  util/

src/
  net/
  http/
  thread/
  log/
  util/
  main.cpp

www/
  index.html

tests/
  simple_test.sh
```

## 4. 核心流程

### 4.1 启动流程

服务启动后会完成以下步骤：

1. 解析命令行参数，包括端口、静态资源目录、线程数、日志文件和 access log 开关。
2. 初始化异步日志。
3. 创建 `TcpServer`。
4. 创建监听 socket。
5. 设置 `SO_REUSEADDR`。
6. 绑定端口并调用 `listen`。
7. 将 listen fd 设置为非阻塞。
8. 创建 epoll 实例并注册 listen fd。
9. 进入主事件循环。

### 4.2 新连接流程

当 listen fd 触发可读事件时，说明有新的客户端连接进入内核已完成连接队列。服务端会循环调用 `accept`，直到返回 `EAGAIN` 或 `EWOULDBLOCK`。

每个新 client fd 会被设置为非阻塞，并注册到 epoll 中，关注：

```text
EPOLLIN | EPOLLONESHOT | EPOLLRDHUP
```

其中 `EPOLLONESHOT` 用来保证同一个 client fd 在同一时间只会被一个 worker 线程处理，避免重复读取和并发处理同一个连接。

### 4.3 请求处理流程

当 client fd 可读时，主线程不会直接处理请求，而是将 `handleClient(fd)` 作为任务放入线程池。

worker 线程会执行：

1. 调用 `recv` 读取数据。
2. 将数据追加到该连接的请求缓冲区。
3. 判断是否已经收到完整 HTTP header。
4. 调用 `HttpParser` 解析请求行和请求头。
5. 根据请求方法和路径构造响应。
6. 调用 `send` 发送响应。
7. 根据 keep-alive 判断关闭连接还是重新注册 epoll 事件。

### 4.4 长连接处理

第一版支持基础 HTTP keep-alive：

- HTTP/1.1 默认保持连接，除非请求头中包含 `Connection: close`。
- HTTP/1.0 默认关闭连接，除非请求头中包含 `Connection: keep-alive`。
- 4xx 错误响应默认关闭连接。
- 空闲连接默认 30 秒后关闭。

为了支持 TCP 字节流中的半包情况，每个连接维护自己的请求缓冲区。如果一次 `recv` 没有读到完整 header，worker 会保留缓冲区内容，并重新激活该 fd 的 epoll 事件。

## 5. 异步日志注解

### 5.1 当前服务器什么时候会写盘？

第一版服务器目前没有真正的业务写盘逻辑。客户端访问 `GET /`、`GET /hello`、`HEAD /hello` 时，只是读取静态文件或返回内存中的 JSON 响应。

当前主要写盘点是日志模块，包括：

- 服务启动日志。
- 新连接建立日志。
- 请求访问日志，例如 method、path、status。
- 错误日志，例如 `accept`、`recv`、`send` 失败。
- 连接关闭和空闲超时日志。

所以第一版里的异步日志主要解决的是：不要让业务线程因为写运行日志而频繁等待磁盘 I/O。

### 5.2 为什么要设计缓冲区？

如果每个 worker 线程处理请求时都直接写文件：

```text
处理请求 -> 写日志到磁盘 -> 返回响应
```

那么磁盘 I/O 变慢时，请求处理线程也会被拖慢。高并发下，日志写入可能变成请求路径上的额外阻塞点。

异步日志的思路是：

```text
业务线程 -> 拼日志 -> 写入内存缓冲区 -> 继续处理请求
后台日志线程 -> 定时或被唤醒 -> 批量写入控制台和日志文件
```

这样可以把业务线程从频繁磁盘 I/O 中解放出来。业务线程只做字符串拼接和内存追加，真正的文件写入交给后台线程批量处理。

### 5.3 两类线程分别做什么？

日志模块里可以理解为两类线程：

- 前台线程：主线程和 worker 线程。它们在处理连接和请求时调用 `Logger::info`、`Logger::warn`、`Logger::error`。
- 后台线程：`Logger` 初始化时创建的 `backendThread_`。它负责从缓冲区中取出日志并写入控制台和日志文件。

前台线程写日志时，会先拿互斥锁，把日志追加到 `currentBuffer_`。后台线程也会拿同一把锁，把待写的缓冲区移动到局部变量，然后释放锁，再执行真正的写文件操作。

关键点是：后台线程写文件时不长期占用锁，否则前台线程会被写盘过程阻塞。

### 5.4 数据一致性怎么保证？

当前日志模块通过一把 `mutex_` 保护共享数据：

- `currentBuffer_`
- `nextBuffer_`
- `buffers_`
- `running_`

多个前台线程同时写日志时，必须先拿到同一把锁，所以不会同时修改 `currentBuffer_`。后台线程搬运缓冲区时，也使用同一把锁，因此不会和前台线程发生内存写冲突。

这保证的是日志缓冲区内部的数据不会被并发写乱。它不是数据库事务级别的一致性，也不保证机器突然掉电时内存里的日志一定不丢。

### 5.5 这个实现是不是完整双缓冲？

当前代码中有：

```text
currentBuffer_
nextBuffer_
buffers_
```

设计意图接近双缓冲：

- `currentBuffer_`：前台线程当前写入的缓冲区。
- `nextBuffer_`：预留的备用缓冲区。
- `buffers_`：已经准备交给后台线程刷盘的缓冲列表。

不过第一版里 `nextBuffer_` 的复用还不完整，所以更准确地说，当前实现是一个异步批量日志模型，带有双缓冲雏形。面试时可以诚实表达为：前台线程写内存缓冲，后台线程批量刷盘，代码保留了双缓冲结构，但还不是工业级成熟日志库。

### 5.6 一直有日志写入会不会堵塞？

会。异步日志不能突破磁盘写入能力的物理限制。

如果日志生产速度长期大于后台线程写盘速度：

```text
日志产生速度 > 日志刷盘速度
```

那么待写缓冲会越积越多，可能导致：

- `buffers_` 占用内存越来越大。
- 前台线程抢锁时间变长。
- 进程内存压力升高。
- 严重时出现 OOM。

OOM 是 Out Of Memory，表示内存耗尽。进程可能申请内存失败，也可能被操作系统杀掉。

工业级日志系统通常会增加：

- 缓冲区数量上限。
- 队列长度限制。
- 日志丢弃策略。
- 阻塞等待策略。
- 按日志级别过滤。
- 日志采样。
- 日志滚动。
- 后台批量写入和异常降级。

第一版没有做这些策略，所以它适合作为学习型异步日志实现，不适合作为无限高压场景下的生产级日志系统。

### 5.7 如果以后有高速写业务，还能直接用双缓冲吗？

可以借鉴双缓冲的思想，但不能只靠双缓冲保证业务数据可靠。

日志和业务数据的可靠性要求不同。日志通常是尽量别丢、顺序大体正确、写慢一点可以接受；业务数据可能要求不能丢、不能重复、不能乱序、写成功后必须能恢复。

如果是访问统计、埋点这类允许少量丢失的数据，可以使用类似模型：

```text
worker -> 内存队列/双缓冲 -> 后台批量写文件
```

如果是留言、任务提交这类中等可靠业务，可以考虑：

```text
worker -> 写 WAL -> 入内存队列 -> 返回成功
后台线程 -> 批量落库或落文件
```

WAL 是 Write-Ahead Log，预写日志。意思是在真正修改业务数据之前，先把“我要执行什么操作”写入一份可恢复的日志。程序崩溃后，可以通过 WAL 重放或修复未完成的操作。

如果是订单、余额、库存这类强一致业务，则应该使用：

```text
worker -> 数据库事务/持久化消息队列 -> 成功后返回客户端
```

这时双缓冲只能作为吞吐优化，不能作为可靠性的核心。

### 5.8 高速写业务还需要解决什么问题？

如果未来挂载真正的高速写业务，需要额外考虑：

- 持久化确认：返回成功时，数据到底只是进了内存，还是已经写入 WAL、数据库或多副本存储。
- 背压：当写入速度超过消费速度时，必须限制队列大小，必要时阻塞、限流或返回 `503`。
- 幂等：客户端重试时，不能重复创建订单或重复扣库存。
- 顺序：同一用户或同一资源的操作需要保证顺序。
- 事务：多个相关写操作要么都成功，要么都失败。
- 恢复：进程崩溃后，要能根据 WAL 或数据库状态恢复。

一句话总结：双缓冲适合降低请求线程等待 I/O 的时间，但它本质是内存削峰，不天然保证业务可靠性。真正的业务一致性要靠 WAL、事务、幂等、背压、持久化确认和恢复机制。

## 6. 已完成功能

第一版已经完成以下功能：

- TCP socket 创建、绑定、监听和关闭。
- 非阻塞 socket。
- epoll 事件监听。
- `EPOLLONESHOT` 防止同一连接被重复派发。
- 固定大小线程池。
- 基础 HTTP 请求解析。
- HTTP 响应构造。
- `GET /` 返回 `www/index.html`。
- `GET /hello` 返回 JSON。
- `GET /xxx` 返回 `www` 目录下的静态文件。
- `HEAD /xxx` 只返回响应头，不返回响应体。
- 404 Not Found。
- 405 Method Not Allowed。
- 400 Bad Request。
- HTTP/1.1 keep-alive。
- 空闲连接超时清理。
- 简单目录穿越防护。
- MIME 类型判断。
- 异步日志和基础批量刷盘。
- 基础自动化测试脚本。

## 7. 编译和运行

在项目根目录执行：

```bash
mkdir -p build
cd build
cmake ..
make
```

启动服务器：

```bash
./tiny_webserver 8080 ../www
```

也可以指定线程数、日志路径和 access log 开关：

```bash
./tiny_webserver 8080 ../www 4 ../logs/server.log 1
```

完整参数格式：

```bash
./tiny_webserver <port> <www_root> [thread_count] [log_file] [access_log:0|1]
```

## 9. 第一版边界

第一版目前只实现了一个轻量级 WebServer 的核心功能，还没有实现以下能力：

- 多 Reactor 模型。
- 完整异步写事件。
- 基于小根堆或时间轮的高效定时器。
- 零拷贝 `sendfile`。
- 完整 HTTP/1.1 协议。
- 请求体解析。
- chunked transfer encoding。
- HTTPS。
- CGI 或动态业务处理。
- 数据库连接池。
- 配置文件系统。
- 更完整的单元测试和压力测试。
- 异步日志背压、日志丢弃策略和日志滚动。

因此，项目更适合定位为学习型、面试型 WebServer，而不是生产环境服务器。

## 10. 面试讲法

重点可以展开讲：

- 为什么使用非阻塞 socket。
- epoll 相比 select 的优势。
- `EPOLLONESHOT` 如何避免同一个 fd 被多个线程同时处理。
- 线程池如何减少线程创建销毁开销。
- keep-alive 如何复用 TCP 连接。
- 如何处理 TCP 半包。
- 异步日志为什么要减少业务线程等待磁盘 I/O。
- 双缓冲日志的收益和边界。
- 为什么当前还不能称为工业级服务器。

## 11. 后续优化方向

后续可以按以下路线继续迭代：

1. 增加更完整的 HTTP 解析能力，支持请求体和更多 header。
2. 将写响应改造成完整的异步写事件，避免 worker 在 `send` 上等待太久。
3. 使用小根堆或时间轮优化空闲连接超时管理。
4. 使用 `sendfile` 优化静态文件传输。
5. 拆分主 Reactor 和从 Reactor，升级为多 Reactor 架构。
6. 增加配置文件，减少命令行参数负担。
7. 增加更完整的单元测试、集成测试和压测脚本。
8. 补充项目架构图和性能测试报告。
9. 给日志模块增加缓冲区上限、日志滚动和异常降级策略。
